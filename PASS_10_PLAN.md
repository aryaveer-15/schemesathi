# Pass 10 sign-in migration plan

**Approval gate.** This is a proposal. Implementation, baseline measurements, the commit and deployment checks belong to Step 2.

## Current token inventory

| Location | What happens today |
| --- | --- |
| server/routes/auth.js | Successful POST /api/auth/register and /login sign a seven-day HS256 JWT with JWT_SECRET, account ID and role. Both return the token and public user in JSON. Registration hashes the password with bcrypt at cost 10. Login compares against a dummy hash for an unknown account and gives the same credential error. |
| client/src/pages/Login.jsx and Register.jsx | Both pass the successful API response, including the token, to signIn. |
| client/src/AuthContext.jsx | On startup, reads and parses schemesathi.auth from localStorage. signIn puts the token and user in React state and writes both to that key. With a token, it calls /api/auth/me on mount and window focus. A 401 or 404 clears the matching session after comparing tokens, including rereading storage. signOut clears memory and removes the key locally. The context exposes the token to consumers. |
| client/src/App.jsx | Reads the token to gate /my-schemes and wires the sign-out action. |
| client/src/pages/FindSchemes.jsx | Reads the token for POST /api/eligibility/matches and calls signOut on a 401. |
| client/src/api.js | Accepts an optional token, constructs the Authorization bearer header and sends it through fetch. Production defaults to a relative API path. Development defaults to localhost:5000 on a separate origin. |
| server/middleware/auth.js | Reads Authorization, bounds and checks the bearer format, verifies HS256 signature and expiry, validates ID, role and expiration, then exposes ID and role as req.user. |
| server/routes/auth.js and server/routes/eligibility.js | GET /api/auth/me uses the authenticated ID to load the public user. POST /api/eligibility/matches requires authentication. The individual scheme check is public. |
| server/app.js | CORS permits the Authorization request header for listed origins. Compression checks for its presence and excludes auth paths. The request logger records only request ID, event, method, route template, status and duration. |

The server has no logout route or session ledger. The runtime auth flow uses neither sessionStorage nor URLs for tokens. The separate schemesathi.language preference belongs to client/src/i18n.jsx.

## Proposed decisions

1. **Cookie and token.** Express will issue a host-only schemesathi_session cookie with HttpOnly, Secure in production, SameSite=Lax, Path=/api and Max-Age=604800 seconds, matching the existing seven-day JWT expiry. Omit Domain. Lax supports ordinary navigation from external links. The write guard below also covers same-site sibling origins. Permit HTTP only for local development. Keep bcrypt and HS256. Require a new signed audience unique to cookie sessions so a copied legacy JWT cannot be replayed as a cookie. Reject duplicate or malformed session cookies and remove bearer authentication. Registration and login return only the public user in JSON.
2. **CSRF.** Before any unsafe API handler runs, require both an exact trusted browser Origin and a fixed non-simple request header, X-SchemeSathi-Request: 1. Reject absent, null or mismatched origins and absent or incorrect headers with 403. Apply to login, registration, logout, both matcher POST routes and future unsafe methods. GET and HEAD must remain read-only. OPTIONS may negotiate a preflight but must never mutate data. Cross-origin forms cannot supply the header and untrusted scripts cannot pass the origin check. The header is deliberately public and requires no stored CSRF token. Direct API clients will need both headers.
3. **Render and development.** Use relative /api and credentials same-origin on Render. Anchor the origin check to the configured canonical HTTPS origin (PUBLIC_SITE_ORIGIN or RENDER_EXTERNAL_URL), never a client-supplied Host or forwarded host. Confirm the actual user-facing domain before rollout and fail closed if configuration is missing. Keep the existing proxy hop configuration. Same-origin production requires no credentialed cross-origin permission. For the existing split-port local setup, allow credentials and the custom header only for explicitly trusted local frontend origins and use credentials include only for the configured trusted development API. Verify the allowed and rejected preflights. Review any separately hosted client before rollout.
4. **Existing users.** At first startup detect and remove only schemesathi.auth, even if malformed, without transmitting or exchanging it. Keep the migration notice in memory. Tell affected users “Sign-in has changed. Please sign in again to continue.” Preserve the language key. Hydrate the public user in memory from /me on startup and refresh on focus. Wait for that check before redirecting a protected page. Distinguish unauthorized from unavailable, and ignore outdated responses after sign-in or sign-out. An older open tab may require a reload. Questionnaire answers remain in memory only.
5. **Logout.** Add an idempotent, CSRF-protected POST /api/auth/logout that expires the same cookie with identical name, path, host scope and security flags, including when the JWT has expired. Return 204 with no-store. Confirm success before reporting sign-out. Offer retry on network failure. A matcher 401 clears stale client state without an extra logout request. Logout removes this browser’s credential. A previously stolen copy of a stateless cookie JWT remains replayable until expiry. HttpOnly also cannot prevent malicious same-origin script from acting as the user.
6. **Existing protections.** Preserve auth write/read limits (20/120 per 15 minutes), eligibility POST limit (90 per minute), proxy-based client separation, the 16 KB JSON limit, existing validators and generic errors. Put logout under the existing auth write limiter. Retain auth and matcher no-store and adapt the compression exclusion for authenticated requests. Keep the logging allowlist. Never serialize request/response headers, cookies, bodies, full URLs or exception objects. Test captured success, rejection and failure logs with sentinel credentials and check Render/proxy logging settings separately.
7. **Deployment and rollback.** Record the current successful Render deployment ID and configuration. Deploy client and API together, verify HTTPS, cookie flags, /me after refresh, guarded writes, logout and the migration notice. No database migration or secret rotation is planned. If the release breaks sign-in, roll back the complete service to the recorded successful deployment in Render, check health and sign-in again, and pause automatic redeployment of the faulty revision. The older release resumes localStorage authentication and ignores the new cookie. Deleted legacy sessions require sign-in again. Before redeploying cookie auth, invalidate cookies left behind by rollback using a fresh cookie-session audience/version so an earlier session cannot silently resume.

## Acceptance after approval

Capture fresh before counts and mobile Lighthouse measurements. Preserve existing test coverage when updating bearer fixtures to use the new transport. Add server and browser checks for registration, login, logout, missing, expired, tampered and legacy tokens, flags and lifetime, origin/header rejection on each unsafe route, and absence of tokens from JSON, browser storage, URLs and application logs. Exercise migration, refresh, language persistence, failed logout and questionnaire privacy. Run the full server and browser suites, axe in English, Hindi and Urdu, 360 px layouts for all 11 languages, and the existing five-route mobile Lighthouse comparison. Preserve scheme data, eligibility logic, translations and visual design. Use existing dependencies. List residual risks before one implementation commit and report measured counts and deployment checks afterward.
